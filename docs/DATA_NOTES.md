# What the data really contains

The dataset README (inside `player_data.zip`, not in git) is checked here against the 1,243 raw files. Where they disagree, the measurement wins.

**Where each number comes from**

- `make profile` → [profile/profile_report.md](profile/profile_report.md). Names in `code style` are metric keys there; each headline metric is stored with its exact definition.
- `make overlay` → [img/](img/) and [profile/orientation_check.json](profile/orientation_check.json). The overlays draw the raw rows of every file, before cleaning, so their legends count humans and bots together.
- `make data` → `web/public/data/`, described in [DATA_FORMAT.md](DATA_FORMAT.md). *(bundles)* marks a number computed from these committed files.
- [profile/crosscheck.md](profile/crosscheck.md): the independent cross-check. All 175 metrics that existed at the time were re-derived blind with no difference. A statement marked *(agent only)* was measured by a cross-check agent and cannot be reproduced from this repo.
- "README says" cells quote or paraphrase the dataset README. *(by hand)* marks something seen once with a shell command.

`ts` values are the raw integers stored in the files. "Human" and "bot" mean the journey's movement event (row 8).

## The five things that matter most

1. **`ts` is Unix time in seconds**, not "milliseconds elapsed within the match". Read as documented, every match would last under one second.
2. **Human or bot is a property of a journey, not of a user_id.** 17 files with a numeric id carry human events. Their ids are placeholders, one per map, not players.
3. **Almost every match is one human and nothing else.** 743 of 796 matches consist of a single file; only 52 include bot journeys; there is no verifiable player-versus-player kill.
4. **The minimaps are not 1024×1024**, and one is not square. The README's formula is right once it is applied to the real image size; its scale may be off by a percent or two (row 21).
5. **Position is recorded about every 5 seconds, and not while a player stands still.** Sample counts show movement, not time spent.

## Cleaning: four rules, applied in this order

Measured by the profiler on the raw files (topic `cleaning`). The profiler's first implementation, the pipeline's `clean.py` and an independent recomputation by the Phase 2 reviewer all arrived at these numbers. The profiler now runs the pipeline's functions, so the numbers are also written out in `pipeline/tests/test_committed_data.py`.

| # | Rule | Rows removed |
|---|---|---|
| 1 | A journey stored in several files keeps one copy: the file in the folder that holds most files of its match | 88 |
| 2 | A file whose second half repeats its first half keeps the first half | 190 |
| 3 | A Kill row is dropped when a Killed row of the same file has the same `ts`, x, y and z | 3 |
| 4 | Movement rows after a death row of the same file, in (`ts`, file order), are dropped | 206 |
| | **Rows left** of 89,104 | **88,617** |

What is left: 1,242 journeys (798 human, of which 17 anonymous; 444 bot). Position 50,931, BotPosition 21,712, Loot 12,829, BotKill 2,406, BotKilled 697, KilledByStorm 39, Killed 3, Kill 0. 739 journeys have a death row, none has two, and no `ts` goes backwards. The build checks the last two and stops otherwise.

## Where the README contradicts itself

1. It calls `ts` time elapsed within the match, yet the timestamps of its two sample rows, from two different matches, read 2026-02-10 12:39:21 and 16:31:22 UTC as Unix seconds (`timestamps > readme_sample_rows`).
2. Its event table makes BotKill and BotKilled human events; its "Bots vs Humans" section gives them to bots.
3. It says a match typically has several humans and bots, but ships 1,243 files for 796 matches.
4. Its filename pattern `{user_id}_{match_id}.nakama-0` adds `.nakama-0` after the match id, while its schema table says the `match_id` value already ends in `.nakama-0`. In the files the name is exactly `user_id + "_" + match_id`.
5. It opens with "battle-royale style game" and later says extraction shooter.

## What this means for the tool

- **Aggregated views carry the value.** With one human per match, "all matches on this map" answers a Level Designer's questions; single-match playback is richest in the 52 matches with bots.
- **Kill zones are places where players stood when they killed bots.** Death zones are mostly places where bots killed players. Neither is player-versus-player.
- **Sample counts show movement, not presence.** Where players wait, loot or hide shows up as time, not as samples.
- **Storm deaths are few and late** (39, all after 10 min 55 s): markers, not a heatmap.
- **Counts differ wildly between maps** (566 / 171 / 59 matches). Every aggregate view has to say how many matches it rests on.
- **"Ignored areas" cannot come from sample counts alone.** Players cross cells between samples, and the artwork includes roofs, rocks and water nobody can walk on. It needs path segments, not points.
